## 它解决什么问题

打开麦麦省看一眼，积分就躺在那儿。攒了半年，换的时候发现——

**你一直在做三件错事。**

### ❌ 错误一：以为「攒大件」更划算

麦当劳积分商场的兑换档位不是等价的。实测（2026-10-23 采样，7 件在售兑换标的）：

| 档位 | 兑换品 | 面值 | 密度（元/积分） |
|---|---|---|---|
| **50 分** | 6.9元可乐麦炫酷 / 香芋派任选 | ¥6.9 | **0.1380** ← 最高 |
| 100 分 | 10.9元指定小食任选 | ¥10.9 | 0.1090 |
| 200 分 | 10.9元指定小食任选 | ¥10.9 | 0.0545 |
| 500 分 | 17.9元板烧可乐组合 | ¥17.9 | 0.0358 |
| **800 分** | 21.9元巨无霸可乐组合 | ¥21.9 | **0.0274** ← 最低 |

**最优档与最差档密度相差 5.0 倍。**

「攒够 800 分换巨无霸」是最差的决策 —— 付出 800 分换回 21.9 元；
而同样的 800 分能换 **16 件 6.9 元券**，面值 **110.4 元**。

所以本项目用 **0/1 背包**求解而不是贪心：在积分预算内最大化现金价值，
并给出**帕累托前沿**，让你自行权衡「花多少分」与「换多少面值」。

### ❌ 错误二：忘了门槛的存在

真实案例（采样自本项目作者账户）：

```
累计获得   1840 分
已过期     1100 分   ← 衰减率 59.8%
当前可用   120 分
最低门槛   50 分       ← 够不到任何一件
健康度     12 / 100（危险）
```

33.5 分对着 50 分门槛，两头挨打：**换不到划算的东西，积分却按期清零。**

这叫**门槛-余额错配死锁**。正确解不是「继续攒」（那只会让更多积分过期），
而是**精确补差** —— 本项目直接算出：再消费 **¥16.5** 就能跨过门槛。

### ❌ 错误三：为早已结束的活动攒分

`mall-points-products` 返回的商城列表**不自动过滤已下架标的**。

实测 50 件标的中，**16 件**积分类标的的 `downTime` 已过。例如：

- `18.8元2份麦辣鸡翅`（200 分）—— 2026-03-21 已下架
- `5.9元香芋派/菠萝派任选`（50 分）—— 2026-06-24 已下架
- `罗技键鼠套装`（6666 分）—— 2026-08-21 已下架

不剔除这些，你会为了一个结束已久的活动白攒分。本项目在采集阶段就计算上下架状态，
**所有计算路径强制过滤**。

## 架构

```
scripts/
  lib/         mcp-client.mjs  schema.mjs        ← 协议与数据契约，无业务
  collect/     parse.mjs  collectors.mjs        ← 纯函数：原始响应 → 契约对象
                normalize.mjs                    ← 快照版本兼容层
  analyze/     coupon-model.mjs                 ← 5 类券建模、叠加互斥、可用时段
                coupon-stack.mjs                 ← 组合计价、最优券组合、凑单陷阱
                coupon-audit.mjs                 ← 沉默成本、同款不同价、券体检
                coupon-schedule.mjs              ← 点单机会预测、二分图最大匹配排程
                diff.mjs                         ← 昨日今日增量（6 类变化）
                asset-plan.mjs                   ← 积分影子价格、积分×券联合决策
                ledger.mjs                       ← 账本、earnRate 校准、复盘
  app/         collect  explore  stores  patrol  dashboard  coupon-report
                execute  render  selftest-*       ← 唯一允许 IO 的层
```

**三条硬约束**：

1. **纯函数优先** —— `collect/` 与 `analyze/` 里的函数是 `(输入JSON) => (输出JSON)`，
   不碰 IO、不读环境变量、不打印
2. **契约先行** —— 跨模块传递的数据结构由 `lib/schema.mjs` 统一定义与校验，
   模块之间不互相 import 内部实现
3. **IO 只在 app 层** —— 只有 `app/` 下的脚本能发起 MCP 调用、读写文件

依赖方向严格单向：`app → analyze → collect → lib`。反向依赖即违规。

**为什么这么分层**：算法层要能同时跑在 Node CLI 和浏览器 Demo 里（双端一致），
所以它必须保持纯函数；采集层要能用**脱敏的历史响应**做离线回归测试，
所以它也不能有 IO。两层分开，各自可测。

## 每天自动检测什么

MCP 没有推送、没有 webhook —— 「每天自动检测」靠**两次快照的差分**实现。

```bash
# 每天跑一次（可挂 cron 或 WorkBuddy 定时任务）
MCD_MCP_TOKEN=<token> node scripts/app/patrol.mjs
```

检出六类变化：

| 变化 | 怎么识别的 |
|---|---|
| 🆕 **新活动** | 活动日历里出现没见过的「日期+标题」 |
| 🆕 **新券** | 卡包里出现没见过的「券名+有效期」 |
| ⛔ **下架** | 之前在售的兑换标的现在不在了 —— 防止为已结束的活动白攒分 |
| ⏰ **临期** | 本月过期的积分 + 7 天内过期的券 |
| 🧾 **你下了一单** | `order-list` 出现新的 `orderId` —— 官方 App 用的同一个账号 |
| ✅ **券被核销** | 上次有、这次没有、且还没到期 |

**第 5 条是闭环的关键**：你在手机上用官方 App 下单后，下一次巡检就能看到它，
进而复盘这一单的实际收益并回校 `earnRate`。

### 积分影子价格 —— 让积分和券能比大小

```
shadowPrice = 可达最优兑换标的的面值 / 所需积分     (元/积分)
```

用**你余额能达到的**最优档，而不是全站最优 —— 全站最优可能是 800 分档，
但你只有 33.5 分，那个密度对你没意义。

```
1 积分 ≈ ¥0.138
  → 376 积分 = ¥51.9
  → 一张 ¥13.5 的券 = 98 积分
  → 「该用券还是该攒分」变成一道可计算的题
```

> 目前 30 个高星参赛项目里只有 1 个做过积分影子价格（maimai-saver #23，115★）。
> 本项目把它做成体系并贯穿到决策层。

### 联合决策：积分 × 券一起排

回答一个具体问题：**你现在有 800 积分和一张 ¥30 的券，该怎么花？**

动作按「零成本 → 有成本」排序：

```
1. 领取 3 张可领券                              [执行]  零成本零风险
2. 50 积分本月过期（约 ¥6.9）                            到期即清零
3. 3 张券 7 天内过期（面值 ¥39.3 ≈ 284.7 积分）         按影子价格折算
4. 用 24 积分抽奖，可抽 15 次                   [执行]
5. 兑换「6.9元可乐麦炫酷」                             密度 0.1380 元/分
```

**临期券折算成积分是关键** —— 284.7 积分 > 抽奖一次 24 积分，用户立刻能判断优先级。

完整公式见 [`references/patrol-algorithm.md`](references/patrol-algorithm.md)。

## 完整闭环

```
┌─ 采集 ──────────┐   ┌─ 决策 ──────────┐   ┌─ 执行 ────────┐   ┌─ 复盘 ─────────┐
│ patrol.mjs      │   │ asset-plan.mjs  │   │ execute.mjs   │   │ ledger.mjs     │
│ 8 项独立容错    │──>│ 影子价格统一折算 │──>│ 强制确认网关  │──>│ earnRate 回校   │
│ 写快照到 data/  │   │ 动作按成本排序   │   │ 执行后自动记账 │   │ 下次更准 ↑     │
└─────────────────┘   └─────────────────┘   └───────────────┘   └────────────────┘
        ↑                                                            │
        └────────────────── 明日巡检 diff 新变化 ←───────────────────┘
```

**闭环的每一环都有实测支撑**：

| 环 | 实现 | 关键点 |
|---|---|---|
| 采集 | `app/patrol.mjs` | 8 项独立容错，单项失败不拖垮全局；写操作默认不执行 |
| 决策 | `analyze/asset-plan.mjs` | 积分影子价格把两种资源拉到同一标尺 |
| 执行 | `app/execute.mjs` | 默认只打印计划，`--confirm` 才执行；执行后记账 |
| 复盘 | `analyze/ledger.mjs` | earnRate 从账户增量反推，回喂决策 |

### earnRate 回校 —— 让补差金额越来越准

`order-list` **不返回每单获得的积分**（实测字段里没有 `earnPoint`），
所以只能从账户积分增量反推：

```
earnRate = (本次累计积分 - 上次累计积分) / 期间有效消费金额
```

有效消费排除**整单退款**与 **0 元订单**（券核销/积分兑换不是新消费）；
部分退款仍全额计入（接口不给退款额，只能如实说明）。

| earnRate | 凑到 50 分门槛要消费 |
|---|---|
| 1.0（默认，未校准） | ¥16.5 |
| 1.3（实测） | ¥12.69 |
| 0.8（实测偏低） | ¥20.63 |

**没有上一次快照时不算** —— 把缺失当 0 会得出「581 分 / 59.4 元 = 9.79 积分/元」
这种荒谬值。此时明确说「跑两次巡检后即可校准」，不编造数字。

```bash
node scripts/app/execute.mjs claim              # 只看计划
node scripts/app/execute.mjs claim --confirm     # 确认执行
node scripts/app/execute.mjs redeem --sku 2001   # 兑换（先看计划）

✗ 积分兑换 无法执行：可用积分 10 不足，需要 50 分（差 40）
✗ 积分抽奖 无法执行：暂不可参与：资源不足
```

完整规则见 [`references/ledger-algorithm.md`](references/ledger-algorithm.md)。

| 算法 | 解决什么 | 实现 |
|---|---|---|
| **积分价值密度** | 每 1 积分换到多少元，识别边际收益率递减 | `rankByDensity()` |
| **四维健康度评分** | 存活率 40% / 变现率 25% / 效率 25% / 临期安全度 10% | `scoreHealth()` |
| **门槛-余额死锁检测** | 找出「够不着也过不了期」的状态并算出精确补差额 | `detectDeadlock()` |
| **0/1 背包 + 帕累托前沿** | 预算内最大化面值，兼顾「花分少 vs 换值多」 | `solveRedeemPlan()` |

外加 **抽奖 vs 兑换的盈亏平衡概率** —— 因为 MCP 不暴露奖品概率分布，
本项目**拒绝编造期望值**，改为给出可独立验证的盈亏平衡点。

完整公式与推导见 [`references/algorithm.md`](references/algorithm.md)。

## 券引擎 —— 让「领得准」有算法支撑

券名是自然语言（`中薯条买一送一` / `王牌小食拼` / `大脆鸡扒堡早餐两件套`），
不建模就只能做字符串匹配。所以券被统一抽象成**可计算的 5 类**。

### 5 类券与判定顺序

| 顺序 | 判据 | 类型 |
|---:|---|---|
| 1 | 买一送一（同一商品打包） | `bundle_price` |
| 2 | 买A送B / 赠品 | `free_gift` |
| 3 | 满X减Y / 立减 | `threshold` |
| 4 | 1+1 / 随心配 / 任选 | `bundle_price` |
| 5 | 单品 X 元 | `item_price` |
| 6 | 单品 X 折 | `percent` |
| — | 认不出来 | `threshold` + 标注不确定 |

**关键区分**：「中薯条买一送一」是组合价（同商品打包），
「买汉堡送香芋派」才是赠品。判错会直接算错价。

### 保守叠加策略

```
拿不准 stackable → 一律视为互斥
两张满减/赠品券 → 可叠加
作用于同一商品 → 互斥
```

**算出的价格必须 ≤ 用户实际支付价。宁可少报优惠，也不给「假便宜」。**

### 「还剩 4 天」≠「有 4 天能用」

券的有效期原文长这样：

```
2026-10-12 10:30-2026-10-16 23:59 周一、二、三、四、五 10:30-23:59   ← 周末完全用不了
2026-10-15 05:00-2026-10-15 10:29 周四 05:00-10:29                  ← 单日券
```

所以券的可用性拆成三个维度：**自然天数** / **真正还能用的天数** / **此刻是否可用**
（早餐券可能明天才生效）。

### 沉默成本

```
你手里有 13 张券，其中 5 张将在 7 天内过期
若未使用，将白白损失 ¥47.5
```

已过期 / 今天到期 / N 天内到期**三类分开统计** —— 紧迫度完全不同。
面值算不出来的券也会单独说明，否则「面值 X 元」会被读成「全部损失只有 X 元」。

### 用券排程（二分图最大匹配）★ 本项目独有

把手里的券**逐张排到未来每一次点单**上 ——「第几单、哪天、用哪张、净价值多少」。

问题建模为**二分图最大匹配**：券 × 点单机会，边 = 那次点单上能不能用这券，
目标是**最大化排得出去的券数**。用增广路算法求解。

**为什么不是「谁先过期先用谁」**：朴素做法会把最灵活的券浪费在最早的一单上。
增广路在匹配失败时会**重新调整已有分配**，把「可用机会最少的券」
留给「可用机会最少的订单」。

排不出去的券会说明原因：「限定周一~周五，未来几次点餐都赶不上」
「可用时段 05:00-10:29，与点餐时间不匹配」。

完整公式见 [`references/coupon-algorithm.md`](references/coupon-algorithm.md)。

## 你的数据存在哪里

本项目会读取你的真实麦当劳数据（积分、券、订单、门店）。这些数据**只存在你自己的机器上**。

| 路径 | 内容 | 是否进版本库 |
|---|---|---|
| `data/snapshot.json` | 资产快照（积分、券、活动、订单、门店） | ❌ 否，已在 `.gitignore` |
| `data/profile.json` | 你的常用门店等偏好 | ❌ 否，已在 `.gitignore` |
| `data/ledger.jsonl` | 决策与执行账本（后续阶段） | ❌ 否，已在 `.gitignore` |
| `.env` | 你的 MCP Token | ❌ 否，已在 `.gitignore` |
| `fixtures/reference/` | **脱敏后的**参考响应，用于离线回归测试 | ✅ 是 |

**为什么 `data/` 整个目录都不进版本库**：

`order-list` 返回的是你的**真实消费记录** —— 门店名、下单时间、金额、单品组合。
这些拼起来是一份完整的**个人消费画像**。公开仓库里放这个既不安全也不体面，
所以整个 `data/` 目录都被排除。

`fixtures/reference/` 里的文件来自其他参赛项目的**脱敏**录制，
只保留了解析逻辑需要的结构，不含可识别信息。

**删除你的全部本地数据**：

```bash
rm -rf data/        # 快照、账本、门店偏好
rm .env             # Token
```

## 券的三个来源，和「先领券再核实门店」

### 券必须三路都查

| 工具 | 口径 | 关键事实 |
|---|---|---|
| `available-coupons` | **账户全域**，不接受任何参数 | 麦麦省可领券，**不限于任何门店** |
| `query-my-coupons` | 账户级，卡包持有 | **唯一能拿到券有效期与限制的来源** |
| `query-store-coupons` | 门店级，该店当前可用 | 口径最窄 |

实测差距：某用户卡包持有 **9 张**，同一时刻该门店只认 **2 张**。
只按门店口径算沉默成本，会把 7 张即将过期的早餐券整个漏掉。

### 所以：先领券，再核对门店

`available-coupons` 是账户全域的 —— **领券这个动作与门店无关**。
所以日常流程是：

```
① 领券（零成本零风险，不需要门店）      auto-bind-coupons
② 定位你的常用门店                       query-nearby-stores → storeCode
③ 核对该店细节                          query-store-coupons + query-promotions
```

第 ③ 步拿到的 `query-promotions` 是**门店级促销**（实测 12 条），
它是「这家店今天有什么优惠」的主力数据源 ——
**这个工具不在官方文档的 33 个工具里**，是本项目的探测器实测发现的。

日常对话里用一句话就能完成：

> 「六道口店今天有什么优惠」

Skill 会自动：领券 → 定位门店 → 拉该店券与促销 → 结合你的积分给出方案。

### 「还剩 4 天」≠「有 4 天能用」

券的有效期原文长这样：

```
2026-10-12 10:30-2026-10-16 23:59 周一、二、三、四、五 10:30-23:59   ← 多日券
2026-10-15 05:00-2026-10-15 10:29 周四 05:00-10:29                  ← 单日券
```

第一张日历跨度 5 天，但只有周一~周五、每天 10:30 之后能用；
第二张**只有当天早上**能用。

所以本项目把券的可用性拆成三个维度：**自然天数** / **真正还能用的时段数** /
**此刻是否可用**（早餐券可能明天才生效）。

## 已知局限

诚实标注，不夸大能力：

1. **抽奖概率未知** —— MCP 不提供概率分布，故不给出期望值，只给盈亏平衡点。
2. **实物类面值无法解析** —— 罗技键鼠、Nike 联名鞋等无价格前缀，被排除在密度排名外。
3. **积分获取速率是估算** —— 默认 1 积分/元，未计入活动加速与等级加成。
4. **不查询外部信息** —— 只用麦当劳官方 MCP 数据。
