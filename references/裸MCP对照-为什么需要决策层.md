# 裸麦当劳 MCP vs 本项目：到底多做了什么

> 全部结论来自 2026-10-23 的真实调用，不是推测。
> 每一项都附了裸 MCP 的原始返回字段。

---

## 一、先纠正一个我自己的错误结论

上一轮我说「App 里看不到是**刚领完还没同步**」—— **这个结论错了**，你的发现推翻了它。

**真相是**：微信小程序和麦当劳 App 是**两个客户端、两套显示口径**，不是同步延迟。

**证据**（你 18:45:17 在麦当劳 App 里新领的 2 张券）：

```
饮料4选1券    tags: [{type:2, value:"app_exclusive", label:"APP可用"}, {value:"pickup"}]
0元小食8选1   tags: [{type:2, value:"delivery", label:"外送专用"}]
```

服务端**明确有 `app_exclusive`（APP 可用）这个标签维度** ——
说明「小程序不显示某些券」是**设计上的口径差异**，不是数据没同步。

对照 7 张券的 tags：

| 券 | orderTypes | tags |
|---|---|---|
| 11.9元麦辣鸡腿堡 | [1,2] | due today, pickup, delivery |
| 19.9元王牌炸鸡任选2 | [1,2] | due today, pickup, delivery |
| **饮料4选1券** | **[1]** | **app_exclusive**, pickup |
| 0元小食8选1 | [2] | delivery |
| 1024"码"力翻倍 | [1] | pickup |
| 11.9元麦辣鸡腿堡(10-30批) | [1,2] | pickup, delivery |
| 19.9元王牌炸鸡任选2(10-30批) | [1,2] | pickup, delivery |

**正确表述**：MCP 返回的是**账户级全集**；小程序、App 各自按自己的场景过滤。
`workbuddy.md` 里我原先写的那段需要修正。

## 二、你的质疑是对的 —— 领券本身确实不用写代码

**裸 MCP 一句话就能领券**：

```

```

实测刚才再调一次（已领完）：

```json

  "datetime": "2026-10-23 18:52:38", "data": null }
```

## 四、五个「裸 MCP 答不出来」的具体现场

### ① 「用券价格 ¥11.9」是省了 11.9 吗？

裸 MCP 给的全部信息：

```json
"discountInfo": { "discountValue": "11.9", "discountDesc": "用券价格",
                  "discountTypePosition": 1, "discountTypeText": "¥" }
```

**没有任何字段说明这是「你付的钱」还是「省下的钱」。**
`discountDesc` 写的是「用券价格」—— 语义要靠读懂中文才能判断。

判错的后果（实测）：当成减免额 → 沉默成本虚高、临期券折算成 148 积分
（而抽奖一次才 24 积分）→「同款不同价」判断完全反向。

**本项目怎么算**（`analyze/coupon-value.mjs`）：

```
① calculate-price 不带券 → originalPrice
② calculate-price 带券码 → price + discount
```

实测六道口店「11.9元麦辣鸡腿堡」：**原价 ¥22.5 → 实付 ¥11.9，实省 ¥10.6**。

⚠️ 关键坑：不带券时可能返回**全 0**（该组合原价不可售），绝不能拿 0 当原价。

### ② 「今天能不能用」要判断 8 个维度

裸 MCP 给的原始字段（每张券约 15 个）：

```
tradeStartDateTime / tradeEndDateTime   有效期
weekdays + isAllTradeTime               星期限制（编码要猜！）
instructions.availableTime              时段
instructions.labels                     渠道
orderTypes / beTypes / channels         适用场景
tags                                    服务端分组
discountInfo                            价值语义
products[].productCode                  适用商品
```

**最隐蔽的是星期编码**：实测 `weekdays: [2,3,4,5,6]`，
同时 `availableTime` 文案写「周一、二、三、四、五」。

→ 数组是 **1=周日**（2=周一…6=周五）。按 JS `getDay()` 解读会得到「周二~周六」
→ **每个周末和每个周一都判错**。

本项目踩过这个坑（三处代码各用一套编码），现在全链统一为 `0=周日`，
且 `checkUsable` 补上了星期判定 —— 裸 MCP 层面根本没人替你做这件事。

### ③ 「还剩 4 天」≠「有 4 天能用」

实测你的一张券：

```
有效期 2026-10-12 10:30 - 2026-10-16 23:59
可用     周一、二、三、四、五 10:30-23:59
```

日历跨度 5 天，但**只有 5 个工作日各半天**能真正用。
一张单日券更极端：`2026-10-15 05:00-10:29` —— 只有当天早上。

**裸 MCP 给了原始字段，但「还有几个可用时段」这个结论必须自己算。**
本项目把它做成三维：`usableDays` / `unusableDays` / `isUsableNow`。

### ④ 「该用哪张券」—— 二分图最大匹配

裸 MCP 的 35 个工具里没有任何排序/推荐工具。

本项目的做法（`analyze/coupon-schedule.mjs`）：
券 × 点单机会建图，边 = 那次点餐能否用此券（星期 + 时段 + 有效期三重判定），
用**增广路**求最大匹配，目标 = 最大化「排得出去的券数」。

**不是「谁先过期先用谁」** —— 增广路在匹配失败时会重排已有分配，
把可用机会最少的券留给可用机会最少的订单。

实测输出（这才是「该用哪张」的答案）：

```
11.9元麦辣鸡腿堡   仅六道口店(595m)可用 → 减 ¥10.6
19.9元王牌炸鸡任选2 两家店都可用        → 减 ¥3.9
1024"码"力翻倍      不限星期，10-29 前  → 减 ¥13.52
```

### ⑤ 「去哪家店能用」—— 三重交叉验证

你今天遇到的实例（实测）：

| 券 | 六道口一号(71m) | 六道口(595m) |
|---|---|---|
| 11.9元麦辣鸡腿堡 | ❌ **计价返回 0** | ✅ 减 ¥10.6 |
| 19.9元王牌炸鸡任选2 | ✅ 减 ¥3.9 | ✅ 减 ¥3.9 |

**根因**：11.9 券适用商品 `1440`（麦辣鸡腿堡）**只在 595m 那家供应**
（一号店菜单 114 项无此商品，六道口店 115 项有）。

裸 MCP 能看到门店券列表，但**要判断「这张券在我要去的店能不能用」，
必须交叉查 `query-meals`（菜单）× `calculate-price`（实算）**。

## 五、还有一个隐性增量：写操作的安全边界

裸 MCP 的写操作是**裸奔**的 —— `draw-lottery` 会直接扣积分，
`mall-create-order` 会直接下单。

本项目加了一层（`lib/mcp-client.mjs` 的 `WRITE_TOOLS` 白名单）：

```
McpError: 工具 auto-bind-coupons 会改动账号状态，已被安全策略拦截。
确需调用时显式传入 { allowWrite: true }，并确保已获得用户确认。
```

执行流程：**默认只打印计划 → 展示代价 → 用户确认 → 执行 → 自动记账**。

实测领券计划（未确认时）：

```
❌ 不会自动执行。先看清楚要领什么、要花多少积分，再决定。
```

## 六、诚实的总结

**你说得对的部分**：领券、查积分、查券列表 —— 裸 MCP 直接能做，
本项目在这三件事上**没有额外价值**。

**本项目真正的增量**（按价值排序）：

| 增量 | 为什么裸 MCP 做不到 |
|---|---|
| **券实际优惠额** | MCP 只给「用券价格」，实省必须跑两次计价 + 判语义 |
| **可用性完整判定** | 8 个维度、含 1=周日 这种编码陷阱，MCP 不解释 |
| **用券排程** | 35 个工具无任何排序/推荐能力 |
| **积分×券统一折算** | 影子价格是本项目定义的度量，MCP 无此概念 |
| **每日增量** | MCP 无推送/webhook，只能靠快照差分 |
| **earnRate 回校** | `order-list` **不返回每单积分**，只能从账户增量反推 |
| **门店可用性** | 需交叉菜单 × 计价，跨 3 个工具 |
| **写操作确认 + 账本** | MCP 是裸奔的 |

**一句话**：**MCP 是数据接口，本项目是决策层。**
MCP 给你 7 张券的原始 JSON，本项目告诉你「今天几点去哪家店、用哪张、净省多少、
为什么明天就作废了」。

**如果没有这个项目**，你得自己做的事是：
读懂 12 条官方未说明的契约、写 2500 行决策逻辑、自己处理时区与单位、
自己核对门店差异 —— 而且大概率会像本项目开发过程中那样，
**在每个周末都判错星期**。

## 七、需要修正的一处文档

`references/mcp-pitfalls.md` 的「九之十二」节把 App 显示差异归因为
「刚领取还没同步」—— **这个表述不准确**，应改为：

> App 与小程序的券是**不同口径**（不是数据错误，也不是同步延迟）。
> 服务端 `tags` 里有 `app_exclusive`（APP 可用）维度，说明客户端按自己的场景过滤。
> MCP 返回账户级全集，是**超集**；引擎以 MCP 为准，但呈现时必须标注适用条件。
