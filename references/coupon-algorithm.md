# 券算法说明

> 本文件记录券引擎（`scripts/analyze/coupon-*.mjs`）的每个公式与判定规则。
> 所有结论都由 `scripts/app/selftest-coupon.mjs` 的 69 项断言覆盖。

---

## 零、为什么要建模

券名是自然语言：

```
中薯条买一送一
王牌小食拼
大脆鸡扒堡早餐两件套
10.9元指定小食任选
```

不建模就只能做字符串匹配 —— 那是「领得准」的反面。建模后每张券都能回答：

| 问题 | 由谁回答 |
|---|---|
| 它能省多少钱 | `parseCouponTerms` / 券自带的 `value` 字段 |
| 它在什么条件下生效 | `checkUsable`（时段/星期/渠道/有效期四维） |
| 它能不能和别的券叠加 | `conflicts` |
| 它值不值得为它凑单 | `analyzeFiller` |
| 它什么时候用最划算 | `scheduleCoupons` |

## 一、5 类券的判定

判定顺序**不可调换** —— 越具体的规则越靠前。

| 顺序 | 规则 | 判据 | 类型 |
|---:|---|---|---|
| 1 | 买一送一 | `买[一1]送[一1]` | `bundle_price` |
| 2 | 买A送B / 赠品 | `买[^送]{1,10}送`、`赠品`、`免费得` | `free_gift` |
| 3 | 满减 | `满X减Y`、`立减X元` | `threshold` |
| 4 | 组合 / 任选 | `1+1`、`随心配`、`套餐价`、`任选` | `bundle_price` |
| 5 | 单品固定价 | 名字以 `X元` 开头 | `item_price` |
| 6 | 单品折扣 | `X折` | `percent` |
| — | 兜底 | 认不出来 | `threshold` + `confident: false` |

### 关键区分：买一送一 ≠ 买A送B

- **「中薯条买一送一」** = 同一商品打包 → `bundle_price`（组合价覆盖两件商品）
- **「买汉堡送香芋派」** = 不同商品 → `free_gift`（赠品不影响价格）

判错的后果很直接：把 `bundle_price` 当 `free_gift` 会漏算组合价；反之会多算。

### 认不出来时保守降级

`confident: false` 时一律按 `threshold` 处理，并在输出中说明
「该券规则无法自动核算，已按单点计」。

**理由**：券面价值 ≠ 实际到手价值。宁可少报优惠，也不给用户一个
到店里付不出来的「假便宜」。

## 二、券面解析

`parseCouponTerms` 从券面文字里抽出可计算参数。

| 参数 | 含义 | 来源 |
|---|---|---|
| `faceValue` | 券面标称价值（元） | 券名里的 `X元` / `立减X元` / `满X减Y` 的 Y |
| `discountPct` | 折扣率（0.5 = 5 折） | 券名里的 `X折` |
| `threshold` | 门槛（元） | `满X减Y` 的 X |
| `unknown` | 面值是否无法确定 | 抽不出数字时为 true |

### 重要的取舍

`faceValue` 是**券面标称价值**，不是实际到手价值。

实测「王牌小食拼」标题里没有数字，从菜单反查原价只能得到 0，
但用 `calculate-price` 传 `couponId` 实测能拿到真实的 6.6 元。

所以本模块**抽不出值时如实标 0 并记 `unknown`**，不编造。
真正的精确价值要靠 `calculate-price` 实测 —— 那是 M4 联合决策阶段的事。

## 三、叠加与互斥

### 保守策略

```
conflicts(a, b) = true  当且仅当：
  ├─ a.stackable ≠ true  或  b.stackable ≠ true     ← 拿不准一律互斥
  ├─ 两者都是 threshold/free_gift                       ← 可叠加
  └─ 作用于同一商品                                     ← 互斥
```

**为什么「拿不准 stackable 一律 false」**：
麦当劳多数单品券、套餐券不叠加。保守的叠加策略意味着
**算出的价格必然 ≤ 用户实际支付价** —— 宁可少报优惠，也不给假便宜。

### 可行组合枚举

券不多（实测卡包 9 张），穷举子集可行（2⁹ = 512）。

`findCompatibleSets` 返回所有互不冲突的组合，按可叠加张数降序。

## 四、组合计价

`priceBasket(basket, coupons)` 的计算顺序：

```
① 逐张处理券
   item_price   → 记录 priceOverrides[code]（取 min）
   percent      → 记录 percentOverrides[code]（取 min）
   bundle_price → 每组挑最贵的那件，打包计入 consumed
   threshold    → 延后处理
   free_gift    → 延后处理

② 算商品小计
   每个商品：eff = min(原价, 改价, 原价×折扣率)
   已被组合价打包的不重复计

③ 满减：取满足门槛的**最大**抵扣（保守，不叠加多张）

④ 赠品：门槛校验后发放

⑤ 实付 = max(小计 - 满减, 0) + 配送费
```

### 三处「不叠乘」

| 场景 | 处理 | 理由 |
|---|---|---|
| 折扣券 + 改价券命中同一商品 | 取 `min` | 真实结算不会两次打折 |
| 多张满减券 | 只取最大的一张 | 保守；麦当劳满减通常不叠加 |
| 组合价券与单品券命中同一商品 | 组合价优先，商品移出小计 | 商品已被打包 |

### 券不适用时明确拒绝

券的适用商品不在购物篮里 → **拒绝并说明原因**，不静默忽略：

```json
{ "rejected": [{ "coupon": "某券", "reason": "券适用商品不在购物篮中" }] }
```

## 五、凑单边际成本

**核心公式**：

```
gap         = 门槛 - 当前小计           （必须补上的钱）
marginalCost = gap - 券面额             （净多花的钱）
worthwhile   = marginalCost ≤ 0
```

### 例子

| 场景 | gap | 券面额 | 净多花 | 结论 |
|---|---:|---:|---:|---|
| 小计 40，券「满35减7」 | 0 | 7 | 0 | 直接可用 |
| 小计 30，券「满35减7」 | 5 | 7 | **-2** | 再点 ¥5 净省 ¥2 ✓ |
| 小计 26，券「满35减7」 | 9 | 7 | **+2** | 再点 ¥9 净多花 ¥2 ✗ |

**「gap」和「marginalCost」不是一回事** —— 这是实现时最容易搞错的地方。
补 ¥9 才能跨过门槛，但券只省 ¥7，所以净亏 ¥2。

## 六、凑单陷阱检测

`detectFillerTraps` 只比较**商品构成相同、仅券不同**的方案对。

**为什么要按商品构成分组**：把完全不同商品组合的方案拿来互比，
会产生大量噪音警告（"你加了汉堡所以更贵" —— 那是废话）。

方案对的指纹：

```
fingerprint(items) = sorted("code×qty" joined by "|")
```

判定：同组内，「用券版本」的 `payable ≥ 「不用券版本」的 `payable` → 报陷阱。

## 七、沉默成本

**核心指标**：

```
atRiskValue = Σ(即将过期券的面值)
```

「即将过期」= 距过期不足 N 天（默认 7 天），含已过期。

### 三类紧迫度分开统计

| 类别 | 判定 | 为什么分开 |
|---|---|---|
| 已过期 | `expireAt < now` | 钱已经扔了，无法挽回 |
| 今天到期 | `now ≤ expireAt < now + 1d` | **最紧迫** —— 今天不用就作废 |
| N 天内到期 | 其余 | 还能抢救 |

**「N 天内」取窗口上限**：9 张券散布在 1~7 天时，写「1 天内」会让人误以为
全部明天就没了，「7 天内」才是准确的紧迫度上界。

### 面值未知的券要单独说

如果某张券的面值无法从菜单推算（`value ≤ 0`），它同样在过期，
只是金额算不出来。**必须说出来**，否则「面值 X 元」会被读成
「全部损失只有 X 元」。

## 八、可用时段 —— 「还剩 4 天」≠「有 4 天能用」

这是本项目「不错过券」的核心。

### 三个维度

| 维度 | 字段 | 含义 |
|---|---|---|
| 自然天数 | `daysLeft` | 距失效还有几个日历日 |
| 可用天数 | `usableDays` | 有效期内真正能用的天数 |
| 此刻可用 | `isUsableNow` | 考虑 `validFrom`（早餐券可能明天才生效） |

### 计算

```
start = max(now, validFrom)
for day in start .. expireAt:
    if weekdays 为空 或 day 的星期 ∈ weekdays:
        usableDays += 1
    else:
        unusableDays += 1
```

### 关键细节

**必须从 `max(now, validFrom)` 开始数**。单日券（如只有 10-15 当天有效）
在今天看来「用不了」，是因为它**还没生效**，不是因为它不生效 ——
这两种情况必须分开，否则会报出「剩余期里有 1 天用不了」这种误导。

### 真实例子

```
2026-10-12 10:30-2026-10-16 23:59 周一、二、三、四、五 10:30-23:59
```
日历跨度 5 天，但只有周一~周五、每天 10:30 之后能用。
如果 10-17/18 是周末，那它们**完全用不了**。

```
2026-10-15 05:00-2026-10-15 10:29 周四 05:00-10:29
```
**单日券** —— 只有当天早上那两三个小时。

## 九、可用性判定（四维）

`checkUsable(coupon, ctx)` 同时判定四个维度，任一不满足即不可用：

| 维度 | 判定 | 不可用时的说明 |
|---|---|---|
| 到账状态 | `status === "可领取"` | 「尚未领取到卡包，需先领」 |
| 有效期 | `expireAt < now` | 「已过期」 |
| 生效日 | `validFrom > now` | 「尚未生效（X月X日起）」 |
| 渠道 | `channel` 不含当前方式 | 「仅限到店使用，当前是外送」 |
| 时段 | `dayWindow` 不含当前小时 | 「可用时段 05:00-10:29，当前不在时段内」 |

**每条不可用都带原因** —— 笼统地说「不可用」没有行动价值。

## 十、用券排程

### 点单机会预测

从历史订单推断未来节奏：

```
cadenceDays = median(相邻订单间隔天数)     ← 用中位数，均值抗不了异常值
```

无历史订单时按每周一次保守估算。

### 分配问题：二分图最大匹配

**这是本项目独有的能力** —— 30 个高星参赛项目里没有第二个做这个。

问题建模：

- 左图：券
- 右图：未来 N 次点单
- 边：这张券在这个订单上**能不能用**（星期 + 时段 + 有效期三重判定）
- 目标：**最大化排得出去的券数**（不是最大化面值）

求解用**增广路算法**（匈牙利算法的增广路版本）。

### 为什么不是「谁先过期先用谁」

朴素做法按到期日顺序分配，会把**最灵活的券**浪费在最早的一单上。

正确做法：把「可用机会最少的券」留给「可用机会最少的订单」。
增广路算法自动做到这一点 —— 它在匹配失败时会**重新调整已有分配**。

举例：

```
券1：只能周四用，10-16 到期
券2：任何时候都能用，10-21 到期
订单：周四 10-15、周六 10-17、周二 10-20
```

匹配结果：券1 → 周四那单，券2 → 后面的单。**两张都排得出去**。
朴素做法若先给券1 排周四，券2 也能排 —— 但如果订单是「周四、周六、周日」，
朴素做法会让券1 占周四、券2 排不上，而最优解是让券2 占周四、券1 排不上也不亏
（因为券1 本来就用不了）。增广路会找到**总数最多**的匹配。

### 排不出去的券要说明原因

这是最有价值的诊断信息：

| 原因 | 说明 |
|---|---|
| 「限定周一~周五，未来几次点餐都赶不上」 | 星期限制 |
| 「可用时段 05:00-10:29，与点餐时间不匹配」 | 时段限制 |
| 「在下一次点餐之前就过期了」 | 有效期 |
| 「排期冲突：更紧的券已经占了这些机会」 | 匹配冲突 |

### 未领取的券不参与排程

还没进卡包的券排了也用不了。它们由体检模块单独列为「先领」。

## 十一、已知局限

诚实标注，避免过度承诺：

1. **券的真实价值需实测** —— 券面价值 ≠ 到手价值。精确值要靠
   `calculate-price` 传 `couponId` 实测，本模块只给券面标称值。
2. **组合券的分组信息需人工补** —— `groups` 字段无法从券名完整解析，
   未解析时该券不参与组合求解。
3. **实物类兑换品无法估值** —— 「罗技键鼠套装」这类标的面值解析为 0，
   不参与密度排名。
4. **点单节奏是估算** —— 实际点单可能不规律，排程给的是**可行安排**，
   不是保证。
5. **不含外部券源** —— 只用麦当劳官方 MCP 数据，不查第三方团购平台。
