# 巡检与联合决策算法说明

> 本文件记录 M3（巡检增量）与 M4（统一资产运营引擎）的公式与判定规则。
> 所有结论由 `scripts/app/selftest-patrol.mjs` 的 38 项断言覆盖。

---

## 一、为什么需要「增量」

MCP **没有推送、没有 webhook**。所谓「每天自动检测到新活动」，
只能靠**两次快照的差分**来实现。

```
昨天 09:00  ──采集──> snapshot.json  ──┐
                                       ├──> diff ──> 「新活动 2 个 · 新券 3 张 · 你下了 1 单」
今天 09:00  ──采集──> snapshot.json  ──┘
```

`diffSnapshots(prev, curr)` 是纯函数，不碰 IO。

### 去重键的选择

| 对象 | 键 | 为什么 |
|---|---|---|
| 活动 | `日期｜标题` | 同一个活动标题会连续多天出现，必须带日期 |
| 券 | `券名｜有效期` | ⚠️ **不能用 couponId** —— 实测同一张券两次拉取的 couponId 不同，但「券名+有效期」稳定 |
| 商城标的 | `spuId` | 稳定的商品 ID |
| 订单 | `orderId` | 唯一的订单标识 |

## 二、检测到的六类变化

### 2.1 新增

```js
newCampaigns   // 新出现的活动（日期+标题都没见过）
newCoupons     // 新进卡包的券
newMallItems   // 新上架的兑换标的
```

**新活动只报标题，不报价格** —— 活动文案里的「9.9元」「13.9r」是营销文案，
无法与门店菜单核实，不可用于任何计算。

### 2.2 下架

```js
delistedMallItems  // 之前在售、现在不是了
```

**这是「别为已结束的活动攒分」的关键** —— 商城列表不自动过滤已下架标的，
只看 `status` 会误导用户。

### 2.3 临期

```js
expiringCoupons    // 7 天内过期的券
expiringPoints     // 本月 / 下月过期的积分
```

### 2.4 你下了一单 ★ 闭环的关键

```js
newOrders = curr.orders 中 orderId 不在 prev 的
```

**orderId 是识别「你在手机上下了单」的精确信号** —— 官方 App 用的是同一个
麦享会账号，所以手机下单后 `order-list` 立刻能看到。

有了它，闭环成为可能：

```
巡检 → 发现新 orderId → 重拉积分与券 → diff → 复盘 → 回校 earnRate
```

### 2.5 券被核销

```js
usedCoupons = 上次有、这次没有、且还没到期的券
```

券用掉后从卡包消失。所以「上次有 + 这次没有 + 还没过期」= 被核销了。
**注意与「过期」区分** —— 过期券也会从列表消失，但它的 `expireAt` 已经过去了。

### 2.6 抽奖变化

```js
lottery.changes = ["单次消耗从 24 改为 30 积分", "新增奖品：X"]
```

## 三、积分影子价格 ★ 核心

**这是本项目让「积分」和「优惠券」能放在同一张表上比较的关键。**

### 定义

```
shadowPrice = 可达最优兑换标的的面值 / 所需积分     (元/积分)
```

### 为什么用「可达的」而不是「全站最优」

全站最优档可能是 800 分（密度 0.0274 元/分），但你只有 33.5 分 ——
**那个密度对你没有意义**。真正能指导决策的是
「你手上的积分能换到的最好档位」。

```
可达最优 = { i : status(i) = live ∧ point(i) > 0 ∧ faceValue(i) > 0 ∧ point(i) ≤ available }
           中 density 最大者
```

### 算完之后能干什么

```
1 积分 ≈ ¥0.138
  → 800 积分 = ¥110.4
  → 一张 ¥13.5 的券 = 98 积分
  → 于是「该用券还是该攒分」变成一道可计算的题
```

| 场景 | 折算 |
|---|---|
| 可用积分 376.3 | ≈ ¥51.9 |
| 本月临期 50 积分 | ≈ ¥6.9 |
| 3 张临期券面值 ¥39.3 | ≈ 284.7 积分 |
| 已过期 17 积分 | ≈ ¥2.3（真实损失） |

> **目前 30 个高星参赛项目里只有 1 个做过积分影子价格**
> （maimai-saver #23，115★）。本项目把它做成体系并贯穿到决策层。

### 边界处理

| 情况 | 处理 |
|---|---|
| 够不到任何在售档位 | 退化为全站最优档作参照，标 `reachableOnly: false`，并提示「优先考虑补差或抽奖」 |
| 没有在售标的 | 影子价格为 0，换算返回 `null` —— **不编造** |
| 已下架标的 | 不参与计算（`status = live` 过滤） |
| 实物类兑换品 | 面值解析为 0，不参与（`faceValue > 0` 过滤） |

## 四、联合决策：积分 × 券一起排

回答一个具体问题：**你现在有 800 积分和一张 ¥30 的券，该怎么花？**

### 动作优先级模型

排序原则：**先做零成本且能避免损失的动作，再做有成本的动作。**

| 优先级 | 动作 | 成本 | 排序理由 |
|---:|---|---|---|
| 1 | `claim_coupon` 领零成本券 | 0 | 不消耗积分，先领完再谈积分，避免沉没 |
| 2 | `points_expiring` 临期积分 | 0 | 到期即清零，是**确定的损失** |
| 2 | `coupon_expiring` 临期券 | 0 | 同上，且能换算成积分说明它有多值钱 |
| 3 | `draw` 抽奖 | 积分 | 把沉没积分转成实物/券期望值 |
| 4 | `redeem` 兑换 | 积分 | 在有更优档位时执行 |
| 4 | `deadlock` 死锁补差 | ¥ | 死锁时的唯一正解 |
| 5 | `campaign` 活动提醒 | 0 | 只做时间线，**不参与金额计算** |

### 临期券为什么要换算成积分

```
3 张券 7 天内过期（面值 ¥39.3）
这些券合计约等于 284.7 积分，按影子价格 ¥0.1380/分 折算
```

**换成积分单位，用户立刻能判断优先级**：
284.7 积分 > 抽奖一次 24 积分 → 先用券。

这是把两种资源拉到同一标尺上的实际价值。

### 死锁的处理

余额够不到任何在售档位时，**不给兑换建议**，而是给补差方案：

```
gap = 最优档所需积分 - 当前可用积分
```

理由：死锁时「继续攒」只会让更多积分过期。正确解是**精确补差** ——
消费刚好跨过门槛的最小金额，立刻兑换高密度档位。

### 活动的处理

活动**只做提醒，不定价**。

```
今天有 2 个活动
gain: { yuan: null, note: "活动文案里的价格不可核实，不计入计算" }
```

「有活动」和「更便宜」是两回事。把营销文案的价格当折扣，是这个领域最常见的误读。

## 五、看板渲染约束

对话内看板要能在**手机上读完**，所以有硬约束：

| 约束 | 理由 |
|---|---|
| 总长 ≤ 40 行 | 手机上不 scroll 到底；有断言守这条线 |
| 变化区在最顶部 | 用户最关心「有什么变了」 |
| 券标「仅 N 天能用」而非「剩 N 天」 | 见 `coupon-algorithm.md` |
| 待办按零成本→有成本排序，写操作标 `[执行]` | 明确区分「要花钱」和「点一下」 |
| 详细数据折叠，提示可追问 | 密度排名、帕累托前沿、排程明细按需展开 |
| 首次运行不显示空的变化区 | 避免「今天没有变化」占屏 |

### 区块结构

```
🍔 麦门日报 · 2026-10-14

**变化行**（有变化时才出现）

💰 积分：余额/累计/已过期 + 影子价格 + 临期告警 + 衰减率
🎫 券包：总数/面值 + 临期券 + 当前不可用券 + 未领 + 同款不同价
🎁 今日活动：标题列表
📌 待办：按优先级排序，每项带成本与理由
🎰 抽奖：活动名 + 单次消耗 + 可抽次数

> 追问可看：过期风险明细 N 条 · 用券排程 N 条 · 同款不同价 N 组
```

## 六、巡检的执行

### 单项容错

每项独立 try，失败记入 `snapshot.errors`，**不拖垮全局**。
借鉴 `maimen-butler` 的 `probe()` 模式 —— 八个巡检项里挂一个，
其余七项的结果照样有效。

### 写操作默认不执行

`auto-bind-coupons` 是写操作（会改动账号状态），**默认不调用**，
需要显式 `--claim`。巡检本身是只读的。

### 快照轮转

```
data/snapshot.json       ← 当前
data/snapshot.prev.json  ← 上一次（保留一轮，用于对比与回溯）
```

两个文件都在 `data/` 下，已被 `.gitignore` 排除 ——
`order-list` 的真实数据含门店、金额与消费习惯，属于个人消费画像。
