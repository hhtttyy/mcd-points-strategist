# 麦当劳 MCP 实测坑位

> 本文件记录**官方文档未说明、但跑通链路必需**的实测契约。
> 每一条都来自真实调用，不是推测。
>
> 官方文档只列了 33 个工具名，**没说清楚每个工具实际返回什么** ——
> 这是本项目最大的隐性成本。
>
> ⚠️ 第一节是**2026-10-23 真实调用后修订过的** —— 早期基于脱敏 fixture
> 得出的结论（"多数工具返回 Markdown"）在真实链路上是错的。

## 一、返回形态：业务 JSON 直挂顶层（2026-10-23 实测修订）⚠️

**实测调用 `https://mcp.mcd.cn` 的返回形态**（不是标准 MCP 信封）：

```json
{
  "success": true,
  "code": 200,
  "message": "请求成功",
  "datetime": "2026-10-23 15:42:51",
  "traceId": "b4b679797a2761cda4ab1f3195462700",
  "data": { ... }
}
```

**没有** `{ content: [{ type: "text", text: "..." }] }` 这层标准 MCP 信封。

| 工具 | `data` 的形态 | 备注 |
|---|---|---|
| `query-my-account` | 对象 | 字段见下 |
| `mall-points-products` | **数组** | |
| `query-lottery-info` | 对象 | |
| `order-list` | `{ list: [...] }` | |
| `query-my-coupons` | `{ coupons: [...] }` | 券的原生结构化字段在这 |
| `available-coupons` | **数组** | `{ couponName, couponImage, couponStatus, label }` |
| `query-store-coupons` | **数组** | `{ title, couponId, couponCode, tradeDateTime, products }` |
| `campaign-calendar` | `{ currentTime, dailyList: [...] }` | |
| `query-nearby-stores` | **数组** | 无收藏时 `data` 字段**直接缺失** |
| `query-promotions` | 数组 | 不在官方 33 工具里，探测发现 |

### 为什么这一条最重要

早期 `rawText()` 只认 `content` 数组，对上述工具**一律返回空字符串**。
结果：解析器在 fixture 上全绿，在真实链路上**券 0 张 / 活动 0 天 / 门店 0 家**，
而且**不报错** —— `errors` 数组是空的，看起来一切正常。

这是本项目最隐蔽的一类 bug：**fixture 骗过了所有测试**。
现在 `fixtures/live/` 保存了原样真实响应，`selftest-live.mjs` 专门守住这条。

### 解析策略（已改为双路兼容）

```js
// 优先吃 JSON，失败再退回 Markdown（保留给旧 fixture）
const fromJson = collectXxxJson(raw);   // 真实结构
const rows = fromJson.length ? fromJson : parseXxxMarkdown(raw);
```

## 二、单位陷阱：两个接口方向相反 ⚠️

这是本项目**最容易造成静默错误**的坑。

| 接口 | 字段 | 单位 | 实测值 |
|---|---|---|---|
| `calculate-price` | `price` / `discount` / `productPrice` | **分** | `1350` = 13.5 元 |
| `mall-*` | `productPrice` / `subtotal` | **分** | `1350` = 13.5 元 |
| `order-list` | `realTotalAmount` | **元** ⚠️ | `"36.5"` = 36.5 元 |
| `mall-order-detail` | `paymentAmount` | **分** | `1350` = 13.5 元 |

**如果把 `order-list` 的 36.5 当分换算 → 得到 0.37 元**，客单价与消费画像会**缩小 100 倍**，而程序不会报错。

> 判别方法：值是整数且带两位小数（`"36.5"`）→ 元；值是整数且无小数（`1350`）→ 分。

**规则**：金额换算只允许发生在 `scripts/collect/parse.mjs`，且每个字段都要明确标注来源接口。

## 四、`query-promotions` 不在官方文档里 ⚠️

**33 个文档工具之外，实测还有一个可用的读工具**：

```
query-promotions   参数：storeCode, orderType, beType
                   实测返回：12 条门店级促销
```

它是**「某门店今日有什么优惠」的主力数据源** —— 官方文档里的 `campaign-calendar` 是**全国活动日历**（不区分门店），而 `query-promotions` 才是门店级的。

> 文档会过时，实测不会。

## 五、券的三个来源，口径各不相同

必须**三路都拉**，缺一路就会漏钱或误判。

| 工具 | 口径 | 关键事实 |
|---|---|---|
| `available-coupons` | **账户全域**，不接受任何参数 | 麦麦省的可领券，**不限于任何门店** |
| `query-my-coupons` | 账户级，卡包持有 | **唯一能拿到券有效期与限制的来源** |
| `query-store-coupons` | 门店级，该店当前可用 | 口径最窄 |

**实测差距**：某用户卡包持有 9 张，同一时刻该门店只认 **2 张**。
若只按门店口径算沉默成本，会把 7 张即将过期的早餐券整个漏掉。

### 推论：先领券，再核实门店

`available-coupons` 是**账户全域**的 —— 领券这个动作**与门店无关**。
所以正确的顺序是：

```
① 先 auto-bind-coupons 领券（零成本零风险，与门店无关）
② 再定位门店，query-store-coupons + query-promotions 核对该店细节
```

不需要为了领券先跑一趟门店查询。

## 六、券的「还剩几天」≠「有几天能用」

`query-my-coupons` 的有效期原文形如：

```
2026-10-12 10:30-2026-10-16 23:59 周一、二、三、四、五 10:30-23:59
2026-10-15 05:00-2026-10-15 10:29 周四 05:00-10:29
```

第一张日历跨度 5 天，但标了「周一~周五」，每天还只有 10:30 之后可用；
第二张是**单日券** —— 只有当天早上能用。

**因此券的可用性必须拆成三个维度**：
1. **自然天数**（`daysLeft`）—— 距失效还有几天
2. **可用时段数**（`usableSlots`）—— 真正还能用的次数
3. **此刻是否可用**（`isUsableNow`）—— 考虑 `validFrom`（早餐券可能明天才生效）

> 未领取的券拿不到这些字段。对「可领取」的券只能给出「未知」，
> **不得说成「无期限」**，也不得编造剩余天数。

## 七、积分商城的两个陷阱

### 7.1 `price` 字段恒为 0，真面值在 `spuName` 前缀

```
spuName: "18.8元2份麦辣鸡翅"   point: 200   price: 0   → 面值 18.8
spuName: "6.9元可乐麦炫酷"      point: 50    price: 0   → 面值 6.9
spuName: "罗技键鼠套装"          point: 6666  price: 0   → 无法解析（实物类）
```

**若误用 `price` 字段，全部积分类标的密度均为 0，排序结果完全失真。**

解析优先级：`spuName` 正则 `^([\d.]+)\s*元` → `price` 字段 → 0（未知）。

### 7.2 `status` 不能单独作为「可兑换」依据

实测 24 个积分类商品里 **15 个兑换截止日已过，但接口状态仍报「上架」**。

只看 `status` 会告诉用户「你有 24 个可以换」，实际只有 9 个。
**必须以 `downTime`（兑换截止日）为准。**

## 八、积分字段是字符串，且可以是小数

```
availablePoint: "376.3"    accumulativePoint: "581.3"    expiredPoint: "17"
```

**积分不是整数** —— 不能用 `parseInt`，必须用 `parseFloat` 语义。
`"376.3"` 若被截断成 `376`，误差虽小但会让临期判断失准。

## 九、活动文案里的价格不可用于计算

`campaign-calendar` 的活动内容介绍里全是价格：

```
超值𝟗.𝟗元早餐两件套陪你开工啦
凭券两件套只要9.9元
麦咖啡13.9r浓浓黑巧来啦！
```

这些是**营销文案**，无法与门店菜单核实。`mall-product-detail` 的 `note` 字段
更是接口自己明确要求「严禁从 note 提取任何数值用于价格计算」。

**规则**：活动日历只取**日期与标题**，用于做时间线与提醒。
**绝不把「有活动」等同于「更便宜」** —— 那是两回事。

## 九之二、活动标题在 `articleDto` 里，不在 `activityTitle` ⚠️

**2026-10-23 实测**：`campaign-calendar` 的 `dailyList[].events[]` 有 17 个字段，
但顶层的 `activityTitle` 是**空串**：

```json
{
  "activityCode": "m228",
  "activityTitle": "",        ← 空串
  "articleDto": {
    "title": "麦当劳「我就喜欢」限定丝巾正式开售🔥",   ← 标题在这
    "content": "丝巾搭配棒球帽的潮流谁懂😎...",
    "highlights": "谁的时尚DNA动了？",
    "buttonText": "立即抢购"
  }
}
```

**踩坑后果**：读 `activityTitle` → 所有活动标题为空数组 →
看板上「今日活动 0 个」，但待办里又说「今天有 1 个活动」—— 自相矛盾。

**正确读法**：`e.articleDto.title`（正文用 `e.articleDto.content`）。

> 这也是参考项目 `maimen-butler` 解析 `articleDto` 的原因。

## 九之三、`discountDesc: "用券价格"` 是「你付的钱」，不是「省的钱」⚠️

**2026-10-23 实测**：卡包券的 `discountInfo` 明确标注了数字的语义：

```json
"discountInfo": {
  "discountValue": "20.48",
  "discountDesc": "用券价格",     ← 关键
  "discountTypePosition": 1,
  "discountTypeText": "¥"
}
```

「1024码力翻倍 ¥20.48」= **龙焰鸡腿堡两件套的到手价是 ¥20.48**，
不是「这张券省了 20.48 元」。

**踩坑后果**：当成减免额 →
- 沉默成本虚高（把到手价当损失）
- 临期券折算积分虚高（¥20.48 → 148 积分，与抽奖一次 24 积分比毫无意义）
- 「同款不同价」判断反向（到手价高的其实是更差的券）

**本项目的处理**：引入独立的 `benefit` 字段。

| `valueKind` | 含义 | `benefit` | 能否参与金额计算 |
|---|---|---|---|
| `coupon_price` | 用券价格（你付的） | `null` | ❌ 需菜单原价对比才能算，没有就不算 |
| `discount_amount` | 减免金额（你省的） | `= value` | ✅ |

**没有原价时一律报「无法推算实际优惠额」，绝不编造。**

## 九之四、券的原生结构化字段（不用从文本正则抠）

**2026-10-23 实测**：`query-my-coupons` 的券对象带完整原生字段：

| 字段 | 内容 | 例 |
|---|---|---|
| `tradeStartDateTime` / `tradeEndDateTime` | 精确到秒的起止 | `"2026-10-29 23:59:59"` |
| `tradeTimePeriods[]` | 每日可用时段 | `[{ startTime: "10:30:00", endTime: "23:59:59" }]` |
| `weekdays[]` + `isAllTradeTime` | 星期限制（空数组 = 不限） | `[]` |
| `instructions.labels[].text` | 渠道标签 | `"到店"` |
| `discountInfo` | 面值 + **语义** | 见上一节 |
| `totalCount` | 该券的张数 | `1` |

**对比从 Markdown 抠「有效期」那行**：
```
2026-10-12 10:30-2026-10-16 23:59 周一、二、三、四、五 10:30-23:59
```
星期与时段混在同一串文本里，单日券（`2026-10-15 05:00-2026-10-15 10:29 周四 05:00-10:29`）
与多日券的语义完全不同，极易判错。**原生字段没有这个问题。**

## 九之五、门店搜索：收藏为空是正常态，不是错误

`query-nearby-stores` 的 `searchType` 决定行为：

| searchType | 必传参数 | 实测行为 |
|---|---|---|
| `1` | `beType` | 收藏餐厅。**没有收藏时返回** `success:false, code:600050, message:"收藏餐厅列表为空…"` —— **`data` 字段直接缺失** |
| `2` | `beType` + `city` + `keyword` | 按位置搜索 |

**踩坑后果**：把 `code:600050` 当错误 → 门店列表永远为空 → 门店券与门店促销全拉不到。

**正确做法**：`collectStores` 对空 `data` 返回空数组（不抛错），
`stores.mjs` 检测到空则**自动降级**为位置搜索，并提示用户。

## 九之六、券的去重键必须用结构化到期时刻

**2026-10-23 实测**：同一张券在卡包与门店两路的 `tradeDateTime` 原文格式不同：

| 来源 | 字段 | 原文 |
|---|---|---|
| 卡包 | `tradeEndDateTime` | `"2026-10-29 23:59:59"` |
| 门店 | `tradeDateTime`（区间） | `"2026-10-23 00:00:00-2026-10-29 23:59:59"` |

**用原文做去重键 → 同一张券被算成两张**，看板上会出现两条一模一样的券。

**正确做法**：去重键用**归一化后的 `expireAt`（ISO 时刻）**，不是原文。

⚠️ 也**不能**用 `couponId` 去重：卡包用 `id`、门店用 `couponId`，语义不同源。

## 九之七、`query-promotions` 返回结构化规则，且忽略传入的 beType ⚠️

**2026-10-23 实测**（六道口店 1950979）：

```json
{
  "promotionId": "331878001",
  "promotionType": "33",
  "ruleCategory": 30,
  "beTypes": ["6"],                          ← 适用渠道
  "startTime": "2025-03-01 00:00:00",
  "endTime": "2026-12-31 23:59:59",
  "products": [{ "type": "2", "productCode": "9900016058" }],
  "ruleDetail": {
    "orderDiscount": { "discount": "26", "startDiscountPoint": "500" }
  }
}
```

语义 = **订单满 500 元减 26 元**。这类规则**可以真正参与计算**，
不像营销文案只能做提醒。

**⚠️ 最重要的坑：该工具忽略传入的 beType。**

| 传入 beType | 返回条数 | 实际 beTypes |
|---|---|---|
| 1（到店自取） | **12** | 全部 `["6"]`（团餐） |
| 2（麦乐送） | 0 | — |
| 6（团餐） | 0 | — |

→ **用 beType=1 查到的 12 条其实是团餐促销，对到店自取不生效。**
实测 `calculate-price` 算 ¥3510 的订单，到店场景减免仍是 **0**，印证了这一点。

**必须按 `beTypes` 过滤，并如实告知「这些是团餐规则，你到店用不上」。**

**另一处结构事实**：同一门槛下有**多条**规则 ——

| 门槛 | 各条减免额 | 单条最高折扣率 |
|---|---|---|
| 满 300 | 22 / 12 / 7 | 7.3% |
| 满 500 | 26 / 16 / 11 | 5.2% |
| 满 1000 | 30 / 20 / 15 | 3.0% |
| 满 2000 | 34 / 24 / 19 | 1.7% |

接口**未说明**同门槛的多条能否同时生效 → 保守按「不叠加」算，
同时给出「若可叠加」的参考值（满 300 → 减 41，13.7%），**不假定**。

**阶梯递减**：门槛越高单条最优折扣率越低（7.3% → 1.7%），
所以最优策略是**刚好压到最低档门槛**，不是买越多越省。

## 九之八、`calculate-price` 才能算出券的实际优惠额 ⚠️ ★

卡包券的 `discountDesc` 是「用券价格」（你付的钱），不是省的钱。
想知道「这张券值多少」，**唯一可靠的办法是跑两次 `calculate-price`**：

```
① 不带券 → originalPrice（原价）
② 带券   → price（实付）+ discount（减免额）
优惠额 = discount / 100
```

**实测六道口店的「1024码力翻倍」**：原价 ¥34.00 → 用券 ¥20.48，
**实省 ¥13.52（39.8% off）**。这比券面数字有用得多。

**⚠️ 两个坑**：

1. **不带券时可能返回全 0** —— 该组合原价不可售（必须用券才能下单）。
   **绝不能拿 0 当原价**（会算出「省了 ¥20.48」的荒谬结论）。
   正确口径是服务端在带券时返回的 `discount`，原价 = 实付 + 减免。

2. **不能用菜单表推算** —— 券的适用商品是**套餐 SKU**
   （如 `9900016523` 龙焰鸡腿堡两件套），常常**不在门店菜单里**
   （菜单只有单品/三件套/四件套），且「套餐原价」≠「各单品原价之和」。

**⚠️ 单位又不一样**：`calculate-price` 的金额是**分**（"3400" = 34 元），
`query-meals` 的 `currentPrice` 是**元**（"26.9"）。
加上 `order-list` 也是元 —— **三个接口两种单位**。

## 九之九、券的三路合并必须逐字段取并集 ⚠️

同一张券在三路的字段分布（实测六道口店）：

| 字段 | 卡包 `my` | 门店 `store` |
|---|---|---|
| `value`（用券价格） | ✅ 20.48 | ❌ 0（接口不返回） |
| `valueKind`（价值语义） | ✅ coupon_price | ❌ 无 |
| `dayWindow` / `weekdays` | ✅ 10:30-23:59 | ❌ 无 |
| `channel` | ✅ pickup | ❌ 无 |
| `itemCodes`（适用商品） | ❌ 无 | ✅ 9900016523 |
| `couponCode` | ❌ 无 | ✅ MCD64C0490… |

**二选一必然丢信息**：选门店那份 → 丢掉「何时能用」与「价值语义」；
选卡包那份 → 丢掉适用商品编码（无法定位菜品、无法测算优惠额）。

**必须逐字段取并集**，且注意：
- **0 不应覆盖非 0**（门店券的 `value=0` 不能盖掉卡包的 20.48）
- `valueKind` 冲突时保留 `coupon_price`（更严格，宁可说「不知道」也不误报）
- 保留 `sources` 数组 —— 记录「这张券在哪些视角下可见」，
  判断「是否在卡包里」要用 `sources` 而不是 `source`
  （合并后 `source` 可能是门店源）

## 九之十、券的 `weekdays` 数组是 **1=周日**，不是 0=周日 ⚠️⚠️ 最隐蔽的坑

**2026-10-23 实测**（六道口店）：

```json
{
  "tradeStartDateTime": "2026-10-19 10:30:00",   // 周一
  "tradeEndDateTime":   "2026-10-23 23:59:59",   // 周五
  "weekdays": [2, 3, 4, 5, 6],
  "instructions": {
    "availableTime": [
      { "text": "2026.10.19-2026.10.23", "type": 1 },
      { "text": "周一、二、三、四、五", "type": 2 },   ← 权威文案
      { "text": "10:30-23:59", "type": 1 }
    ]
  }
}
```

**决定性证据**：同一张券的 `availableTime` 文案写着「周一、二、三、四、五」，
而 `weekdays` 是 `[2,3,4,5,6]`。

| 解读方式 | 结果 | 与文案 |
|---|---|---|
| 0=周日（JS getDay） | 周二~周六 | ✗ 矛盾 |
| **1=周日（getDay+1）** | **周一~周五** | ✓ 一致 |

**所以数组编码是 1=周日，比 JS `getDay()` 大 1。**

**错位的实际后果**：

| 日子 | 真实 | 按 0=周日 解读 |
|---|---|---|
| 周六 | 不可用 | **判为可用** ✗ |
| 周一 | 可用 | **判为不可用** ✗ |

**每个周末和每个周一都会判错。**

**本项目因此踩了三次**（同一份数据被三处用不同编码解读）：

| 位置 | 原编码 | 后果 |
|---|---|---|
| collect 原生数组 | 原样透传（1=周日） | 与文本解析不一致 |
| collect `parseWeekdays`（文本） | 0=周一 | 与原生数组差一天 |
| analyze `computeUsableSlots` | 0=周一 | 与 collect 差一天 |
| analyze `forecastOrders` | 0=周一 | 同上 |

**修复**：全链统一 **0=周日**（= JS `getDay()` 原生语义），
collect 层把原生数组 `.map(n => n - 1)` 转过来。

**更好的做法**：**优先用 `instructions.availableTime` 的文案**（服务端原文），
不要从数组反推 —— 数组编码有坑，文案不会错。

## 九之十一、`checkUsable` 必须判星期，否则「仅 N 天能用」会误导

券的可用性有五个维度，缺一不可：

| 维度 | 字段 | 缺失后果 |
|---|---|---|
| 到账状态 | `status` | 把没领的当已领 |
| 有效期 | `expireAt` / `validFrom` | 把过期当可用 |
| 时段 | `tradeTimePeriods` | 早餐券当全天券 |
| 渠道 | `instructions.labels` | 到店券当外送券 |
| **星期** | **`weekdays`** | **周一~周五的券在周六被判可用** |

实测：一张限「周一~周五」的券，看板只说「仅 5 天能用」，
用户会以为每天都能用 —— 实际周六去不了。
补上后能给出「仅限周一、周二、周三、周四、周五使用，今天是周六」。

## 九之十二、App 卡包与 MCP 的券是**不同口径**（不是数据错误）

**用户现象**：手机 App 卡包只有 2 张券，MCP `query-my-coupons` 返回 5 张。

**实测证明券是真的、可用**：

```
calculate-price 带券码计价：
  11.9元麦辣鸡腿堡   原价 ¥22.5 → 实付 ¥11.9  减 ¥10.6
  19.9元王牌炸鸡任选2 原价 ¥23.8 → 实付 ¥19.9  减 ¥3.9
```

**App 与 MCP 显示的是同一批券，只是口径与命名不同**：

| | App | MCP |
|---|---|---|
| 命名 | 营销名（「麦辣鸡腿堡汉堡」「龙焰2件套」「得来速0元薯饼」） | 标准品名（「11.9元麦辣鸡腿堡」「1024码力翻倍」「免费脆薯饼」） |
| 范围 | 当前场景**立即可用**的子集 | 账户**全部**券（超集） |
| 门店 | 按当前定位门店过滤 | `query-my-coupons` 不绑门店 |

实测证据：
- 5 家门店的券**完全相同**（同 couponId / 同 tradeDateTime / 同券码）
- 外送渠道（orderType=2）无券；得来速（beType=5）与到店相同
- 券的 `bigImage` 文件名即营销名（`麦辣鸡腿堡汉堡.png`、`王牌小食自由拼.jpg`、`龙焰2件套.jpg`）

**规则：引擎以 MCP 为准**（它是超集），
但**呈现时必须标注适用条件**（星期/时段/渠道），
否则用户会像这次一样困惑「App 里怎么没有」。

## 十、抽奖不暴露概率分布

`query-lottery-info` 返回奖池、奖品列表、消耗规则，但**不返回中奖概率**。

任何点估计期望值都是编造。本项目的做法是给**可证伪的盈亏平衡概率**：

```
设单抽消耗 d 积分，同额积分直接兑换可得 redeemValue = d × bestDensity
设奖品价值区间 [worst, best]，抽中最高价值的概率为 p
E[抽奖] = p·best + (1-p)·worst
令 E[抽奖] = redeemValue 解出 p* = (redeemValue - worst) / (best - worst)
```

`p* ≤ 0` → 抽奖的最低价值已不低于兑换，直接抽；
否则 `p*` 就是盈亏平衡点 —— 概率未知时结论是「不确定」，不是伪造的期望值。

**是否可参与以 `drawDecision.resourceEligible` 为准**，
**不要从 `availableTimes` 推断**。

## 十一、写操作工具清单（探测器一律不调用）

| 工具 | 副作用 |
|---|---|
| `auto-bind-coupons` | 一键领取全部麦麦省券（改变账户状态） |
| `create-order` | 创建点餐订单（**可能真实扣款**） |
| `cancel-order` | 取消订单 |
| `mall-create-order` | 积分兑换下单（**扣积分**） |
| `draw-lottery` | 消耗积分抽奖 |
| `party-order-create` | 主题活动下单 |
| `delivery-create-address` | 新增配送地址 |

`scripts/lib/mcp-client.mjs` 的 `WRITE_TOOLS` 集合是唯一白名单，
`callTool` 默认拦截，**必须显式 `{ allowWrite: true }` 才能调用**。

### 重试策略的差异

- **429**（限流，每分钟 600 次）→ 指数退避重试，尊重 `Retry-After`
- **5xx** → **不重试**。下单类接口重试可能造成**重复下单**。
- **401** → 立即失败，提示去 open.mcd.cn 重新激活 Token

## 十二、Token 与安全边界

- Token 从 `MCD_MCP_TOKEN` 环境变量或项目根 `.env` 读取，**永不写入日志**
- `.env` 与 `data/` 必须在 `.gitignore` 里 —— `order-list` 的真实数据含
  门店名、金额、消费规律，是**个人消费画像**
- MCP 无「积分怎么获得」接口 —— 只能查余额、查商城、抽奖。
  **攒积分做不了**，这是接口供给的空白，不是选题失误
