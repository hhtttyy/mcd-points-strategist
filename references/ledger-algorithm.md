# 执行与复盘算法说明

> 本文件记录 M5（写操作确认网关 + 账本 + earnRate 回校）的规则。
> 所有结论由 `scripts/app/selftest-execute.mjs` 的 31 项断言覆盖。

---

## 一、为什么需要账本

MCP 给的是**现在的状态**，但决策依赖**历史的关系**。

最典型的例子是 `earnRate`（1 元消费能得多少积分）。没有历史数据就只能用默认值 1.0 ——
而默认值错了，**补差金额就会算错**：

| earnRate | 凑到 50 分门槛要消费 |
|---|---|
| 1.0（默认假设） | ¥16.5 |
| 1.3（实测） | ¥12.69 |
| 0.8（实测偏低） | ¥20.63 |

所以本项目把「每次决策与执行」记进账本，用真实数据回校参数。

---

## 二、账本结构

`data/ledger.jsonl` —— 一行一条 JSON，便于追加与流式处理。

```json
{
  "ts": "2026-10-13T19:02:00.000Z",
  "action": "redeem",
  "target": "6.9元可乐麦炫酷",
  "costPoints": 50,
  "costYuan": 0,
  "gainYuan": 6.9,
  "note": "50 积分 → 面值 ¥6.9",
  "meta": { "tool": "mall-create-order", "items": ["6.9元可乐麦炫酷"] }
}
```

| 字段 | 含义 |
|---|---|
| `ts` | 记录时间（ISO） |
| `action` | `claim` / `redeem` / `draw` / `order` |
| `target` | 动作对象（券名 / 商品名 / 奖品名） |
| `costPoints` | 消耗积分 |
| `costYuan` | 消耗金额（一般为 0，下单不在本项目范围） |
| `gainYuan` | 预期收益 |
| `note` | 人类可读说明 |
| `meta` | 附加信息（调用的工具、涉及的条目） |

**解析容错**：坏行跳过而不整体失败 —— 账本可能被手工编辑过。
CSV 导出时含逗号/换行的字段会被正确转义。

## 三、earnRate 校准 ★ 核心

### 关键约束：`order-list` 不返回每单积分

实测订单字段：

```
orderId, orderType, createTime, beType, beCode, storeCode,
storeName, orderStatus, orderProductList, realTotalAmount
```

**没有 `earnPoint`** —— 无法直接读「这一单得了多少积分」。

所以只能从**账户积分增量**反推：

```
earnRate = (本次累计积分 - 上次累计积分) / 期间有效消费金额
```

这个口径的优势：它包含了活动加速、会员等级加成等**所有**因素，
是真实净值而非理论值。

### 有效消费金额的口径

| 订单类型 | 计入？ | 理由 |
|---|---|---|
| 订单已完成 | ✅ | 正常消费 |
| **整单退款** | ❌ 排除 | 钱退了，积分通常也退，这不是消费 |
| **0 元订单** | ❌ 排除 | 券核销 / 积分兑换，不是新的消费 |
| **部分退款** | ✅ 全额计入 | ⚠️ 接口不提供退款额，**只能如实提示「支出可能略偏高」**，不猜退款额 |

> 部分退款会让 earnRate 略微偏高。这是已知的口径限制，**不假装精确**。

### 置信度

| 样本量 | 置信度 | 理由 |
|---|---|---|
| 1 单 | `low` | 一个订单可能碰上活动加成，代表性不足 |
| 2–4 单 | `medium` | 有参考价值但不稳固 |
| ≥ 5 单 | `high` | 可用于决策 |

### 边界：缺失的上一次快照

**不能把缺失的 `prevAccount` 当作 0**。

那会把「累计获得 581 分」误当成「本期赚了 581 分」，
算出 `581 / 59.4 = 9.79 积分/元` 这种荒谬值。

判断依据是**字段是否存在**，不是值是否为 0 —— **0 是合法的基线**。

```
hasPrev = prevAccount && prevAccount.accumulative !== undefined && prevAccount.accumulative !== null
```

没有上一次快照时，返回 `earnRate: null` + 说明「跑两次巡检后即可校准」，
**不编造数字**。

### 分母只能用本期新增订单

不能用全部历史订单 —— 那会算出「累计积分 / 全部历史消费」这种无意义的数。
必须用 `diff.newOrders`（本次巡检识别出的新订单）。

## 四、闭环接线

这是本模块存在的意义 —— 参数要真的回到决策里：

```
巡检 → diff 识别新订单 → Δ累计积分 → earnRate 校准
                                    ↓
                        回喂 asset-plan 的死锁补差计算
                                    ↓
                    看板显示「📈 earnRate 实测 X 积分/元」
                                    ↓
                    执行 → 记账 → 下次复盘比对偏差
```

### 死锁补差随 earnRate 变化

```js
gap         = 最优档所需积分 - 当前可用积分
spendNeeded = gap / earnRate
```

`earnRate` 标注了是实测值还是默认值 —— 看板会区分显示，
不让人以为那个数字有多可靠。

## 五、复盘：预期 vs 实际

### 复盘三类资产

| 类别 | 对比什么 |
|---|---|
| **积分** | 实测 earnRate vs 原先假设的 1.0 |
| **券** | 预测的面值 vs 实际核销省下的钱 |
| **抽奖** | 消耗的积分 vs 实得的奖品价值 → 每积分回报 |

### 偏差阈值

earnRate 偏差 **≥ 0.05 才报** —— 太小的不报，避免噪音。

```
实际 0.4377 vs 默认 1 → 偏差 -0.56 → 报
   → 「攒分比预想的慢，补差要花更多钱」
```

### 抽奖 ROI 的意义

```
抽奖 1 次，消耗 24 积分，实得约 ¥3
→ 每积分回报 ¥0.125，对照兑换密度可判断抽奖是否划算
```

对照影子价格 ¥0.138/分 —— 这次抽奖的实际回报（¥0.125）**低于**直接兑换。
这个判断只有做了复盘才能得到。

## 六、写操作确认网关

三个写操作，全部经过 `app/execute.mjs`：

| 动作 | 工具 | 代价 |
|---|---|---|
| `claim` 领券 | `auto-bind-coupons` | 不消耗积分，券进卡包 |
| `redeem` 兑换 | `mall-create-order` | 消耗 N 积分，每件单独成单 |
| `draw` 抽奖 | `draw-lottery` | 每次消耗 N 积分，概率官方不公布 |

### 四条铁律

1. **先展示，后执行** —— 执行前必须打印清单与代价
2. **显式确认** —— 必须带 `--confirm`
3. **默认拒绝** —— 不带 `--confirm` 时只打印计划
4. **执行后记账** —— 每次执行写一条账本记录

### 前置校验

执行前会拦住这些情况：

```
✗ 积分兑换 无法执行：「21.9元巨无霸可乐组合」已于 2026-10-01 23:59:59 下架，不要为它攒分
✗ 积分兑换 无法执行：可用积分 10 不足，需要 50 分（差 40）
✗ 积分抽奖 无法执行：暂不可参与：资源不足
```

**下架标的被拦住**尤其重要 —— 那是「为已结束的活动白攒分」的直接防线。

## 七、已知局限

1. **部分退款无法精确扣除** —— 接口不提供退款额，earnRate 会略偏高
2. **earnRate 有滞后** —— 需要至少两次巡检才能算出增量
3. **记账依赖用户主动执行** —— 在官方 App 下的单不经过本项目，只能通过
   `order-list` 差分反推
4. **抽奖奖品价值需人工标注** —— 接口不提供奖品定价，账本里的 `gainYuan`
   来自执行时的记录
